# 千问图片预处理与批量识别调研

日期：2026-10-17。范围：本机 LM Studio 的实际配置、官方预处理实现、小规模受控对照。此研究不改变现有检验工作台，也没有启用正式模型接入。

## 结论先行

1. **会调整尺寸。** 图片进入视觉模型前，可能先被应用层限尺寸，再被模型处理器缩放到视觉网格；原图有多少像素，不代表最终全部进入模型。
2. **裁掉无关背景有明确的工程价值，拼图没有必然优势。** 同一批裁片可以作为多张独立图片放进一次请求，也可以拼图；两种方式都应比较，不能预设拼图更快、更准。
3. **先以 1～4 件的小批量为候选。** 后续按最小文字尺寸、总视觉 token 和真实样本验证决定批量。看不清或疑似差异的元件可单独再次识别；整体检测结果仍按完整任务汇总。
4. 本轮只有四个不同的合成元件。8 件、16 件是重复排布，**不能把清晰布局全部读对解释为生产准确率 100%**。
5. **已经出现因拼接布局而漏读差异的反例。** 16 件方形拼图全部抄录正确；同样裁片排成长条，经最长边限制缩小后，四个 `SV385` 都被读成 `SV358`。因此必须把尺寸和布局约束写进输入策略。

### 图片经过哪些处理

下面是目标接入链路；其中本系统的自动定位、旋转仍属于后续实施，不表示已接入当前第一阶段工作台。

```text
原始照片（保留作为证据）
  → 我们的处理：纠正 EXIF、定位、保留边距裁剪、必要时旋转
  → 模型请求中的图片：独立多图或编号拼图
  → LM Studio 图片输入尺寸限制
  → 千问处理器：近似保持宽高比，按像素预算和 32 像素网格调整尺寸
  → 像素数值归一化、分块、视觉编码
  → VLM 输出
```

“像素数值归一化”是把数值映射到模型所需范围，和缩小图片分辨率是两回事。模型权重的 4bit 量化也不表示图片被压成 4bit。

### 千问处理器的规则

官方模型预处理配置以及本机配置均包含 `patch_size=16`、`merge_size=2`，因此该实现的空间网格为 32 像素；本机处理器设置最小 65,536 像素、最大 16,777,216 像素。

这些上下限表示**总像素面积**，不是“最长边 16,777,216 像素”。处理器尽量保持宽高比，在网格取整和像素预算下调整宽高；不会因为这些规则自动把器件摆正、定位丝印或裁出各个器件。非常细长的图还受到处理器宽高比限制。

近似视觉 token 数可按 `调整后宽度 × 调整后高度 ÷ 1024` 估算；文本、特殊标记、参考图和输出还要另留上下文空间。不能直接把处理器允许的 16.8 MP 用满，因为当前加载的 16k 上下文还需要容纳其他内容。

依据：[Qwen3.8 官方预处理配置](https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/preprocessor_config.json)、[MLX-VLM 图片处理实现](https://github.com/Blaizzy/mlx-vlm/blob/main/mlx_vlm/models/qwen3_vl/processing_qwen3_vl.py)。本机实际代码的版本和 SHA-256 另存于研究环境快照，网络主分支可能继续变化。

### LM Studio 额外限尺寸

官方发布记录明确说明默认图片附件最长边 2048，并可在 Settings → Chat → Image Inputs 调整。本机设置也确实是 2048。

例如 4096×3072 的照片若先缩为 2048×1536，原来 40 像素高的字约剩 20 像素高。拼成更大的白板，并不会绕过这一步。增加白边也会占用画面及视觉 token，模型不会因为背景没有内容就自动免除相应空间成本。

本轮还用 960×960 与 3072×3072 的同内容探针核对 SDK 和 REST 调用路径，证据见下面实测记录。不能仅根据聊天界面设置推断所有 API 版本的行为。

依据：[LM Studio 官方发布说明](https://lmstudio.ai/blog/lmstudio-v0.3.31)。

### 与其他软件同时运行的关系

本次查到的缩放规则由配置和图片尺寸决定，没有发现“因为其他软件运行，就临时自动降图片分辨率”的机制。其他软件会竞争 CPU、GPU 和统一内存，可能使推理变慢、排队、内存不足或失败。

如果未来我们主动设计负载降级策略，也不应悄悄降低检验图片分辨率；优先控制并发和排队，并明确记录任何分辨率变化。

## 二、对照测试设计

输入来自仓库已有 `fixtures/inspection/four-components.png`，其人工核对真值保存在 `fixtures/inspection/expected.json`：四个元件三行字依次为 `SV358/A26/0147`、`SV358/A26/0147`、`SV385/A26/0147`、`SV358/A26/0147`。

- 固定人工选区，裁出四张 430×430 的裁片，不缩放其内容。保留相同原始角度，用于隔离布局变量；本轮**不验证自动定位或自动旋转**。
- 白板每格 480×480，在元件外放置编号，不遮挡文字；各元件保留原始裁片背景，没有替换器件内部颜色。
- 独立多图是“一次请求中含多张图片”，与“多个并发请求”不同；本轮所有请求串行。
- OCR 对照不向模型提供真值或标准文字，不把前一次回答放进后一次请求。
- 对照逐字符、逐行核对全部内容，并检查元件数量、编号、顺序和差异元件位置。
- 另做一次“正品图 + 四件拼图”的真实多图文字比对，核对模型输出的 PASS/FAIL。
- 温度参数 0，SDK 请求关闭思考，每轮最多 55 秒，轮间停 3 秒，检查内存/负载/系统热状态；没有可用的具体温度读数。

实测结果和尺寸探针结论见随附 `research/vision-batching/results-2026-10-17.json`。耗时包含图片准备上传、模型预填充和生成，不包括人工裁剪时间及轮间休息；每种配置只做一次，不能用微小耗时差给方案排定优劣。

### OCR 布局实测结果

“正确”指该元件三行文字全部精确一致，不只是首行看起来相似。

| 方案 | 请求图片尺寸 | 全文正确元件数 | 差异件文字是否读对 | 本次请求耗时 |
| --- | --- | --- | --- | --- |
| 四件各自单独请求 | 每张 430×430 | 4/4 | 是，1/1 | 合计 12.9 秒 |
| 原始四件照片 | 1536×1024 | 4/4 | 是，1/1 | 16.8 秒 |
| 一次传四张独立裁片 | 四张 430×430 | 4/4 | 是，1/1 | 8.1 秒 |
| 四件紧凑白板 | 960×960 | 4/4 | 是，1/1 | 9.4 秒 |
| 八件紧凑白板 | 1920×960 | 8/8 | 是，2/2 | 21.6 秒 |
| 十六件方形白板 | 1920×1920 | 16/16 | 是，4/4 | 35.6 秒 |
| 四件低分辨率压力图 | 手动缩至 512×512 | 4/4 | 是，1/1 | 5.5 秒 |
| 十六件横向长条白板 | 7680×480 → 约 2048×128 | **12/16** | **否，0/4** | 13.4 秒 |

8 件与 16 件仍只含四种源裁片；512 图只是压力测试，**不是本机默认缩到 512**。本组样例文字较短、清楚、有重复性，不能据此给实拍长字符串确定安全分辨率。

长条和方形图拼接前的总像素数相同、使用相同裁片和相同抄录提示词；长条触发最长边缩放，方形图未触发。引擎实际展开后的上下文从方形图的 3,721 token 降至长条图的 377 token。模型仍返回完整的 16 个编号，但把 #03、#07、#11、#15 的 `SV385` 全读成 `SV358`，没有用 `?` 表示看不清。若直接按这些抄录内容判断一致性，四个文字差异都会漏检。该实验同时改变了空间排布及实际缩放结果，不能把全部误差单独归因于某个插值算法。

这也说明，**有完整 JSON、元件数量正确、模型没有表达不确定，仍不能证明识别正确**。批量策略需要外部尺寸约束和实拍验证。

### 参考图加待检拼图

另一次请求同时传入正品原图和四件白板图，模型实际输出 `PASS、PASS、FAIL、PASS`，三行抄录也均正确，用时 19.5 秒。这里只验证文字比对，没有验证外形、颜色、图案及可变丝印规则。不能把这一耗时与无参考的 OCR 请求直接当成同一负载比较。

### 2048 限制的 SDK / REST 探针

用相同内容的 960×960 和 3072×3072 图，只要求极短输出，观察引擎真正展开后的上下文长度：

| 通道 | 960×960 输入 | 3072×3072 输入 | 对照解释 |
| --- | --- | --- | --- |
| 本项目 SDK 传输 | 923 token | 4,119 token | 减去相同文本与标记后，分别对应 900、4,096 个视觉 token |
| `/v1/chat/completions` REST | 963 token | 4,159 token | 同样对应 900、4,096 个视觉 token |

900 对应 960×960 的 32 像素网格；4,096 对应 2048×2048，而非原始 3072×3072 应有的 9,216。因此两个本机通道都符合 2048 上限。这里根据引擎 token 展开和处理器规则交叉核验，未修改服务端来导出内部图片张量。

SDK 探针的 API `prompt_tokens` 两次都仅报告 25，REST 探针都仅报告 65，**并未反映实际视觉展开量**。后续做输入预算与性能监测，应区分 API 统计和引擎真实视觉 token；不能凭这两个数字相同就认为没有缩图或图片成本相同。

## 三、如何把结果用于系统设计

### 建议的输入策略

1. 原图原样保存；从原分辨率直接裁剪，保留器件外形、引脚和适量边距。不要先缩小整张大图再定位裁剪用于识别。
2. 正品图也做同类处理，并保持“参考图”和“待检图”角色清楚。参考图和待检图不需要强行拉成相同宽高或同样颜色。
3. 首选比较“一次传 2～4 张独立裁片”和“紧凑的 2×2 编号拼图”，保留逐件识别作为基线。优先方形或适度矩形布局，避免把很多元件拼成长条。
4. 记录请求前尺寸、预期缩放后尺寸、裁剪坐标、旋转变换、编号映射、模型及预处理版本。所有输出 ID 必须和输入一一对应；漏件、重号或非法 JSON 不能作为完整结果提交。
5. 对疑似字符、低置信度或图案差异的元件，使用原分辨率裁片单独复判。若裁片本身仍模糊，提示重新拍照。不能通过生成式超分辨率补笔画来决定合格。

### 批量的上限应看什么

同样是四个元件，字体大小、原图像素、器件占比和拼接形状不同，实际可辨识度也会不同。批量上限应结合：

- 经所有缩放后的最小字符高度、细笔画和字符间距；阈值需用实拍数据校准，现阶段不编造统一安全值。
- 视觉 token 总量（包括正品参考）和当前上下文预算。
- 漏件、串号、近似字符误读、异常件被多数相似良品“带偏”的情况。
- 单件与整组耗时、失败后的重试成本；合并更多元件不保证更高吞吐。

双三次或 Lanczos 放大可以让小图更容易呈现给模型，但不能恢复相机没有拍到的真实笔画。把小图放大后再被服务缩回去，通常只增加处理步骤。

### 正式选型前需要的实拍验证

拿到华为平板后，同一组物理元件分别拍单件、4 件、6 件、8 件，覆盖短丝印、长字符串、`S/5`、`O/0`、`I/1`、小差异、反光和不同角度。逐件裁片、多图同请求、紧凑拼图、原始多件照片使用相同样本做配对比较。

至少分别统计全文逐字一致率、元件定位/数量正确率、差异检出率、**不合格误判为合格**、误报、无法判定/需重拍、编号对应正确率，以及耗时中位数和较慢尾部。测试集按不同物理元件和拍摄批次划分，不能把同一张图的重复拼接当作大量独立样本。

最终批量大小、是否拼图、清晰度阈值以及自动复判条件，应由这些数据确定。本轮尚未验证外形/颜色/图案差异的批量判断，也没有把批量策略接入正式工作台。

## 四、复现与文件

在仓库根目录运行（使用现有本地 Python 环境，不会下载或加载模型）：

```bash
.venv/bin/python research/vision-batching/benchmark.py
```

要求 `hr-qwen` 已在本机 LM Studio 加载，端口 1234。脚本复用仓库已有受限 SDK 传输，默认跳过已保存案例；仅此研究进程移除代理环境变量，避免回环请求误走 SOCKS。推理超时或资源压力时停止，不自动反复重试。

完整图片、环境快照、未经助手纠错的模型原文与资源记录在忽略入 Git 的 `outputs/vision-batching-20261017/`。可复现脚本、精简结果和本文分别保存在 `research/` 和 `docs/research/`。
