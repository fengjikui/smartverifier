# 模型选型与图像预处理：初步调研及汇报素材

日期：2026-10-17。阶段：初步筛选与本机受控实验。用途：形成后续技术汇报的原始材料，支持下一步实现与实拍验证。**尚未确定生产模型和服务器规格。**

## 1. 当前判断

1. **本机部署小模型已经可行。** 本轮在 Apple M2 Ultra / 64 GiB 上实际运行了完整视觉版 Qwen3.5-4B，以及 CPU 上的 PP-OCRv6 small。普通办公电脑和最终 NVIDIA 服务器的表现需要另测。
2. **4B 值得优先进入下一轮验证。** 四个合成元件的丝印全文和一次参考图比对都读对了，但一次多图响应未遵守约定的对象结构。不能仅看读字，还要测结构化输出、说明遵循和复杂外观判断。
3. **纯读字值得单独用 OCR 比较。** 同样四张裁片，PP-OCRv6 small 的 CPU 推理合计约 0.88 秒，文字全部一致；这不覆盖图案、颜色、外形及自由文本检验说明。
4. **定位与最终识别应分开选型。** 简单背景可先用传统视觉做基线；复杂背景可比较专用轻量检测器；精细分割仅在收益明确时增加。
5. 当前最值得实现和比较的路线是：`定位/旋转裁剪 → OCR 或 2～4B VLM → 规则/视觉比对 → 必要时 27B 复判`。其中自动路由及合格放行条件尚未验证；不能直接按小模型的自报置信度放行。

## 2. 先拆开四类任务

| 任务 | 输入 / 输出 | 适合的技术 | 选型时真正要测的点 |
| --- | --- | --- | --- |
| 元件定位 | 原图 → 每个元件的框或轮廓 | OpenCV、专用检测器、提示式定位模型 | 漏件、重叠、背景干扰、框是否保全器件 |
| 姿态处理和排版 | 框/轮廓 → 旋转裁片、编号拼图、坐标映射 | OpenCV + Pillow 即可，通常不需要大模型 | 不切掉文字/引脚，避免多次插值，保留对应关系 |
| 丝印与外观读取 | 裁片 → 逐行文字、图案/外观观察 | OCR、轻量 VLM | 近似字符、长型号、反光、模糊、少数异常件被混淆 |
| 按标准判断 | 正品图、检验说明、观察结果 → 结论及证据 | 规则 + VLM，必要时独立视觉比较 | 可变内容、现场说明、冲突提示、结构化输出和漏检 |

白板拼接本身不需要“生图模型”。应直接使用真实裁片排版，保留原图和变换记录；不能通过生成式修复重绘丝印或引脚。相机原图上的编号、模型输入里的编号、报告中的元件必须可反向对应。

## 5. 定位、抠图与旋转候选

| 路线 | 能做什么 | 轻量性 / 使用条件 | 初步建议 |
| --- | --- | --- | --- |
| [OpenCV 轮廓 + 最小旋转框](https://docs.opencv.org/4.x/dd/d49/tutorial_py_contour_features.html) | 在背景反差明显时定位外轮廓、估计倾角、裁剪 | 无额外模型权重；阈值和几何规则依赖拍摄环境 | **首先作为可解释、低成本基线**，用干扰和漏件样本验证 |
| 专用轻量检测器，例如 [YOLO OBB](https://docs.ultralytics.com/tasks/obb/) | 一次输出多个带角度的元件框 | 需要自有器件和背景标注；通用预训练权重不等于现成电子元件检测器 | 真实背景下若传统视觉不稳，优先比较此路线；不一定需要精细 mask |
| [MobileSAM](https://github.com/ChaoningZhang/MobileSAM) | 根据点/框提示输出轮廓；也有自动 mask 生成 | 原版全流程约 9.66M；提示来源和自动 mask 去重/筛选仍需解决 | 若精细分割确实改善检测，再做轻量分割候选 |
| [SAM 2.1 Tiny](https://github.com/facebookresearch/sam2) | 点/框提示分割和自动 mask | 官方约 38.9M；速度数据依硬件，不能套用到本机 | 作为精细 mask 质量对照；无需为静态器件引入视频流程 |
| [Grounding DINO](https://github.com/IDEA-Research/GroundingDINO) + SAM | 用文本找目标，再细分割 | 比专用检测器复杂；“电子元件”零样本召回和小件效果待验证 | 更适合辅助标注和探索，不作为首轮最轻路线 |
| [Florence-2 base / large](https://huggingface.co/microsoft/Florence-2-base) | 提示驱动的定位、OCR、区域任务 | 官方模型表约 0.23B / 0.77B；能力依任务和样本 | 可作辅助定位对照，尚未验证工业元件识别 |

Ultralytics 的代码和模型采用 AGPL-3.0 / Enterprise 双授权，集成方式需与公司要求核对，见[官方授权说明](https://www.ultralytics.com/license)。这不表示所有名为 YOLO 的实现或所有小型检测器都采用同一授权。

### 技术上需要特别区分

- **裁片和精细抠图不同。** 保留少量原背景的旋转矩形裁片可能已满足识别，并保全引脚；精细 mask 若切掉细引脚或改变边缘，会影响外观比较。其收益要通过实验判断。
- **摆正外形和摆正文字不同。** 矩形有 180° 歧义，近方形还可能有 90° 歧义；轮廓角度不能保证文字向上。需要文字方向判断或受约束的候选方向识别。
- **倾斜和透视不同。** 小角度旋转不能完全修正透视；只有四角和边界可靠时再进行透视变换，避免把器件几何特征改坏。
- **mask 不等于类别识别。** SAM 自动输出的许多区域仍要选出哪些是完整元件、去重并保全数量。小字 OCR 的检测框也不能替代整个器件定位。

## 6. 本轮实际实验

### EXP-002：4B 与 27B 的同输入对照

本机：Apple M2 Ultra、64 GiB、macOS 15.7.4、LM Studio 0.4.12+1。4B 是已在本地的 `mlx-community/Qwen3.5-4B-4bit` 完整视觉版本，API 确认支持 vision。模型文件总量约 3.06 GB；这是磁盘占用，**不是峰值运行内存**。

4B 临时实例 `sv-research-qwen4b`，上下文 8192、并行 1；27B 基线上下文 16384、并行 1。所有比较输入均能装入两者上下文。均使用各自原生模板的请求副本关闭思考、温度 0、同一提示词及相同输入字节，保留 2048 图片上限。

四个不同的合成元件文字为 `SV358/A26/0147`，其中第三件第一行是 `SV385`。这些样本字少且清楚，不能代表真实长丝印、字体磨损或允许变化的批号。

| 输入 / 任务 | 27B 本次结果与耗时 | 4B 本次结果与耗时 |
| --- | --- | --- |
| 四张裁片分别请求 | 全文 4/4，合计 12.9 秒 | 全文 4/4，合计 **5.7 秒** |
| 原始四件照片 | 全文 4/4，16.8 秒 | 全文 4/4，**4.2 秒** |
| 一次传四张独立裁片 | 全文及结构通过，8.1 秒 | 文字人工/离线核对 4/4；**对象结构不合约定**，2.6 秒 |
| 四件方形拼图 | 全文及结构通过，9.4 秒 | 全文及结构通过，**3.0 秒** |
| 正品图 + 四件拼图，文字比对 | `PASS/PASS/FAIL/PASS`，19.5 秒 | 同样结论和全文正确，**5.4 秒** |

4B 的第一次单件请求 2.574 秒，后三次约 1.0 秒，存在预热影响。每种条件仅一次；输出格式长度也会影响耗时，不据此宣称稳定倍速。只对比文字及明确文字差异，未测图案、颜色、封装、自由文本规则和真实误放行率。

**结构失败原文**为一个带 Markdown 代码围栏的 JSON 数组 `[{"id":1,"lines":[...]}]`，要求则是 `{"items":[...]}`。它是合法 JSON，但不符合对象契约；本轮没有偷偷包装成成功，也未请求模型补答。原评分器把结构不符统称为 `json_valid=false`，本轮将评分区分成 `json_valid` 与 `schema_valid`，保留旧评分和原文。这是评分口径修正，不是模型识别能力提升。

### EXP-003：CPU 专用 OCR

用已有本地权重 `PP-OCRv6_small_det + PP-OCRv6_small_rec`，CPU 两线程、识别 batch=1、关闭方向分类和文档矫正、检测最长边最多 1280。输入与 VLM 单件对照相同的四张 430×430 原始角度裁片，未向 OCR 提供参考答案。

| 元件 | OCR 三行结果 | 单次推理 |
| --- | --- | --- |
| 1 | `SV358 / A26 / 0147` | 0.2501 秒 |
| 2 | `SV358 / A26 / 0147` | 0.2126 秒 |
| 3 | `SV385 / A26 / 0147` | 0.2128 秒 |
| 4 | `SV358 / A26 / 0147` | 0.2089 秒 |

四张全文均正确，推理合计 0.8844 秒；初始化另需 3.6816 秒。CPU OCR 是本进程调用，VLM 是经 LM Studio API 调用，两者任务、输出、通信开销不同，不能把耗时比当作完整检验系统的加速比。未测 OCR 自动元件分组，逐行顺序使用文字区域中心排序，复杂多列或斜排还需另测。

### EXP-004：现有 OpenCV 定位基线与反例

使用仓库已有实验代码 `inspection/vision.py`，OpenCV 4.13.0、两线程。以下时间包括定位、旋转裁剪和裁片 PNG 写入，不含输入图另存及 Python 初始化。

| 输入 | 真实元件数 | 返回区域数 | 本次时间 | 发现 |
| --- | --- | --- | --- | --- |
| 单件参考图 | 1 | 1 | 0.0940 秒 | 数量相符 |
| 单件差异图 | 1 | 1 | 0.0870 秒 | 数量相符 |
| 四件照片 | 4 | 4 | 0.1201 秒 | 数量相符，能生成旋转裁片 |
| 空背景 | 0 | 0 | 0.0222 秒 | 提示未可靠定位 |
| 只有一个深色矩形干扰物 | **0** | **1** | 0.0232 秒 | **把非元件误当元件** |
| 重复排布八件图 | **8** | **4** | 0.1589 秒 | 代码找到八个候选后按旧规则截取前四个，并发出提示 |

最后一项是**旧实验实现硬编码四件上限**，不是 OpenCV 理论上只能定位四件。当前不把旧代码原样接入新工作台，也没有在本轮修改其规则。目视查看第一张旋转裁片，主要丝印与引脚清楚，边缘还带入邻近器件的一小段引脚，说明裁剪边距与相邻区域需进一步处理。

这里只核对数量与部分裁片呈现，没有像素级 mask 真值、框 IoU 标注或生产召回率；不能把前三张成功写成“自动定位准确率 100%”。

## 7. 资源与后续 NVIDIA 部署

本轮没有下载新模型，也没有新建生产推理服务。所有推理串行；开始前及运行间检查负载、可用内存和系统热状态。测试结束卸载本轮创建的 4B 实例，原有 27B 实例保留空闲；OCR 进程已退出。未发现系统热告警，没有具体温度传感器读数。

以纯权重理论估算，4bit 的 2B / 4B / 27B 分别约需 1 / 2 / 13.5 GB；实际还包含未量化层、视觉编码器、嵌入、量化元数据、KV 缓存、视觉激活和运行工作区。**不能用这个公式直接购买显卡。** 本机 4B 转换文件约 3.06 GB，就是实际文件与纯参数估算不同的例子。

NVIDIA 上应重新确认框架、模型架构和量化后端支持，测相同视觉细节预算下的峰值显存、并发队列、吞吐、首 token、完整结果和尾部延迟。当前 Mac 的延迟只能作为本机记录；100 个在线用户不等于同时运行 100 次推理。

## 8. 下一步建议及实施衔接

### 下一轮选型顺序

1. 用 4B 完整视觉模型继续做真实器件测试，并加入 2B；以 27B 保持同输入对照。
2. 用同一实拍集比较 PP-OCRv6 small 与 VLM 的文字部分，分开测近似字符和长型号；不取消图案/外形判断要求。
3. 非千问路线先选 InternVL3.5 小模型与 Gemma 4 E2B 各一款，逐个运行；不同时下载、加载全部候选。
4. 先看传统定位在真实统一背景中的失效比例。若不能可靠覆盖，标注真实元件框，比较专用轻量检测器；有必要再加 MobileSAM / SAM 2.1 Tiny 精细分割。

### 原本计划的下一实施阶段

原计划先把真实链路接入新版平板工作台：`原图上传 → 自动定位 → 裁剪与旋转 → 现有 27B 识别及参考图比对 → 结构化结果 → 进度/详情/报告`，保留首阶段已完成的增量检测、重拍替换、可选修正和任务汇总规则。

这轮研究后，建议仍先用现有已验证的 27B 打通链路，同时将定位器、OCR/VLM 和输入布局做成可替换适配模块。随后在同一套照片及工作台中切换 4B/2B/OCR 组合比较，减少把流程问题误判为模型问题的风险。IDaaS、MES 真接口及正式管理端仍按后续阶段推进。

### 正式结论前还缺什么

真实平板照片及人工真值；多种封装和字体；允许变化的丝印；反光、近似字符、模糊和相邻元件；标准/现场说明冲突；模型输出结构稳定性；不良误判为合格、误报、需重拍率、元件对应准确率、端到端延迟及内存。

对于“小模型先判、大模型复判”，还应测试**小模型自信但判断错误**的样本，评估独立规则、交叉读取和抽样复判策略；不能只将模型自报低置信度的样本交给大模型，就宣称安全等效。
