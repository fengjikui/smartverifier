# 丝印检测轻量模型选型与当前协议实测

日期：2026-11-01。结论适用于当前“整图识别 + 正品图比对 + VLM 定位 + VLM 判断照片质量”的链路。本文保留官方资料、工程判断和实验反例，供选型及后续汇报复用。

## 1. 先给结论

1. **当前默认是 Qwen3.8-27B、MLX 4bit，服务实例 `hr-qwen`。** 本机文件约 16.08 GB，上下文 16384、并行 1。没有切换日常业务模型。
2. **更小模型值得做，但现有 4B 还不能只改模型名就上线。** 本轮走当前完整协议，4B 的单件约 6.1 秒，双件约 6.0 秒，四件约 9.9 秒；双件、四件因坐标越界被系统拒绝。四件还出现异常文字对应到错误元件的问题，双件误把型号差异当作需重拍。速度不能脱离有效结果讨论。
3. **整套替换的优先候选是 MiniCPM-V 4.7-1B 与 Qwen3.5-2B；已有 4B 继续用于任务拆解后的对照。** 这不是已验证的准确率排名。MiniCPM 的命名 1B 对应当前 HF 权重统计约 1.55B；不能用文件名代替总参数或内存测量。
4. **最低资源的方向是专用 OCR。** 优先比较已有 PP-OCRv6 small 与 Xiaomi-OCR-0；再用 PaddleOCR-VL-1.6、MiniCPM-OCR 1.0、GLM-OCR 做对照。OCR 更适合读字，不能直接承接全部图案、外形、自由文本规则与正品比对责任。
5. **暂时保留 27B 基线。** 先在隔离环境验证小模型，再决定完整替换还是采用“同事的定位模块 + 单元件 OCR/小 VLM”。不恢复旧 OpenCV 分离或传统清晰度门槛。

OCR 路线不是一定不能接自然语言提示：上述部分 VLM 型 OCR 能做提示式提取；但传统 PP-OCR 的读字接口与通用 VLM 的检测说明语义不同。需要分别验证“读到了什么”与“这些差异是否被标准允许”。

已有的 **2026-10-17** 实验：PP-OCRv6 small 在 CPU 两线程对四张 430×430 合成裁片转写，四张全文正确，推理合计 0.8844 秒，初始化另需 3.6816 秒。该结果本轮仅复核旧记录、没有重跑；不包括元件定位、自由文本规则、照片质量判断和外观比对。见[旧实验](模型选型与图像预处理-初步调研及汇报素材-2026-10-17.md)与[原始数据](../../research/model-selection/results-2026-10-17.json)。不能拿它和完整 VLM 时间直接算系统加速倍数。

### 3.3 Jev：核验转写，不代替正品判定

前面提到的名字也找到了一个与本任务直接相关的模型：[MiniCPM-OCR Jev](https://huggingface.co/openbmb/MiniCPM-OCR-Jev)。它基于 Qwen3.5-2B，保留视觉与语言部分，用分类头评价“原图区域 + 候选 OCR 内容”是否一致，返回分数；本轮权重统计约 2.21B。它不是主要的转写模型。

例如照片确实写着 `SV385`，OCR 也正确读成 `SV385`，Jev 完全可能给高分；但若正品要求 `SV358`，业务仍须判不合格。不能把 Jev 的转写正确分数直接当作合格率或已校准的真实性概率。是否引入这层，需要比较减少的错误与新增的推理开销；本轮未部署。

## 4. 小模型为何还要特别配置图像处理

- **MiniCPM-V 4.7**：官方处理器提供 16x／4x 视觉压缩；4x 为细节保留更多视觉 token，适合加入丝印对照，但会增加开销。还应固定高分辨率切片数量。不能只用默认最快模式评价细字能力。其 [grounding 指南](https://github.com/OpenSQZ/MiniCPM-V-CookBook/blob/main/inference/minicpm-v4_7_grounding.md)使用 0～1000 的 `[x1,y1,x2,y2]`，本系统要转成 0～1 的 `[x,y,w,h]`，禁止在未知语义时猜测修复。
- **Gemma 4**：官方可配置视觉 token 预算，细字应比较 560／1120 等高预算；不能用面向概览的低预算结果替代 OCR 验证。还需使用该模型推荐的图文顺序，不能为统一参数强行套用千问的模板。
- **Qwen／InternVL**：固定输入分辨率、处理器版本和切片配置后再比较；模型收到相同 PNG 不代表内部使用相同视觉 token。减少像素、减少切片与缩小参数是不同的优化，记录时分开。
- **量化**：BF16 公榜不等于 4bit 转换效果；对可疑字符及近似字体应做 Q4／Q8 或 BF16 的小范围对照，先排查量化和输入预算，不直接断定是模型规模的问题。

这些是官方配置能力与本项目的试验建议，不是已经测得的优劣。[MiniCPM-V 配置](https://huggingface.co/openbmb/MiniCPM-V-4.7-1B)、[Gemma 4 配置](https://huggingface.co/google/gemma-4-E2B-it)、[InternVL 模型说明](https://huggingface.co/OpenGVLab/InternVL3_5-2B)。

## 5. 当前完整协议的本机对照：EXP-20261101-A

### 条件与记录

- 使用仓库生成样片：单件、双件、四件，共三张 1536×1024 照片，合计七个元件实例；主要只包含 `SV358/SV385` 两种短丝印模式。**不是七个独立业务类别，也不是实拍准确率测试。**
- 两个模型各做三次请求，每场景一次；先 27B 后 4B，全部串行，不统计稳定 p95 或长期吞吐。
- 相同样片、同场景参考图、检测说明、业务协议、Schema、原图管线；各用原生模板，关闭思考，上下文 16384、并行 1、最大输出 6000 tokens、超时 90 秒。没有关闭校验或猜测补框。
- 使用 `LocalVisionPipeline.prepare/recognizePhoto`，不是临时简化成只读三行字。Schema 约束通过请求参数发送；依然执行应用侧完整校验。不同模板产生的 prompt token 数不完全相同。
- 明确使用独立的 `outputs/small-model-survey-20261101/state`，不写日常正品或检测数据库；本轮候选实例 `sv-survey4b-20261101` 测试后已经卸载，`hr-qwen` 保留。
- 模型耗时为工作器内本次调用计时，首输出为追踪器看到第一个正文片段的时间；含本机协议及图像准备开销，不等于 GPU 内核计时。SDK token 统计保留原值，不能据此反推模型内部视觉 token 数。

### 结果

| 场景 | 27B 调用／首输出 | 27B 当前协议 | 4B 调用／首输出 | 4B 当前协议 |
| --- | --- | --- | --- | --- |
| 单件 | 19.68／14.38 秒 | 通过，文字及合格结论正确 | 6.09／4.85 秒 | 通过，但框明显偏大 |
| 双件，一件型号错序 | 23.85／13.38 秒 | 通过，按位置 `PASS/FAIL` | 6.03／3.18 秒 | **拒绝：两个框越界**；另把文字差异归成 `needs_recapture` |
| 四件，左下型号错序 | 42.63／22.97 秒 | 通过，按位置 `PASS/PASS/FAIL/PASS` | 9.93／5.10 秒 | **拒绝：四框均为 `[1,1,1,1]`**；原文异常对应到 C01，预期为 C03 |

27B 生成正文分别 167／324／592 tokens；4B 分别 149／340／561 tokens，reasoning tokens 均报告为 0。因此本轮速度差不能归因于 27B 输出了大量思考文本，也不是 4B 完全省掉了多件结果。失败输出的时间不计为成功检验吞吐。

### 失败说明

4B 双件原文 C02 返回 `[0.58,0.36,0.91,0.78]`，按当前宽高协议有 `x+w>1`、`y+h>1`；四件所有框都是 `[1,1,1,1]`。这些均为合法 JSON，基本类型／各元素范围也可以符合 Schema，但不满足矩形的关联约束。结构化生成不能保证模型真的理解了坐标，更不能保证文字归属正确。[vLLM Schema 接口](https://docs.vllm.ai/en/latest/features/structured_outputs/)解决输出格式约束，业务校验与语义验证仍需保留。

单件 `[0.35,0.29,0.64,0.71]` 虽在范围内，但比 27B 返回的局部范围宽很多，可能涉及坐标语义混淆；没有人工框真值，不作精确 IoU 判断，也不擅自按右下角坐标转换成“成功”。

本轮没有测忽略区、重点区、自由文本冲突、磨损／强反光、长型号和连续实拍；27B 三次通过同样不能证明它在这些场景可靠。

### 资源与完整证据

每次推理前和结束后使用现有资源守卫，CPU 两线程，内存不足 8 GiB 或出现系统热／性能压力时停止。本轮七次快照的最小可用内存约 13.27 GiB；没有系统热告警，无具体温度读数。两个模型同时驻留有额外开销，该可用内存不是任何单模型的峰值显存。GPU 峰值分配本轮未测。

## 6. 资源预算与部署取舍

如果所有权重元素都恰好为 4bit，纯元素存储下限约为：2.27B → 1.14 GB，4.66B → 2.33 GB，1.55B → 0.78 GB。实际包还含未量化模块、视觉投影、量化元数据及嵌入；运行另需视觉激活、工作区、KV／状态缓存和服务进程。不能用这些下限购买显卡。本机 4B 的实际文件是 3.06 GB，而非理论 2.33 GB。

| 环境 | 可执行做法 | 不应预设 |
| --- | --- | --- |
| 当前 Mac | 已有 4B 可用独立实例继续对照；新候选分批下载、串行推理 | MLX 包能原样用于 Windows／NVIDIA |
| Windows + NVIDIA | 为目标架构选择 Transformers／vLLM／受支持的 GGUF；固定视觉模块和量化文件 | 有 GGUF 文件就表示当前 LM Studio 已完整支持该架构和多图 |
| Windows 普通 CPU | 先评估 PP-OCR small；GGUF 小 VLM 可以做验证，但必须测完整耗时 | 2B 一定能稳定在几秒内完成多件整图判定 |
| 公司 GPU 服务 | 通过现有 `SV_VLM_ENDPOINT/MODEL` 及兼容 API 接入，验证多图、Schema、模板和超时 | 修改地址就等于模型语义已经兼容 |
| 手机／平板 | 当前继续作为浏览器客户端，服务器推理 | 本轮需要改成端上推理；官方端侧演示等于当前设备已验收 |

若采用“小模型优先 + 27B 复判”，两者同时常驻本机不一定降低峰值内存；需要将大模型放到服务器、按需加载，或在硬件预算中接受共同驻留。按需加载又有冷启动代价。小模型自报高置信度、Jev 分数或 OCR 分数，都不能直接作为自动放行依据。

## 7. 下一轮怎么选，避免一直换模型却没有结论

### 第一轮：最低接入成本，解决已知失效点

1. 当前 27B 保持基准。固定目前快照，不用新结果覆盖旧记录。
2. 4B 分成两种任务：A 为整图定位／计数，B 为已经指定一个元件区域后的正品比对。各自评价，不把 B 成功包装成 A 成功。是否改成两阶段要先做隔离实验，不直接改生产管线。
3. 加入 MiniCPM-V 4.7-1B 和 Qwen3.5-2B，先跑相同三场景和失败反例；对 MiniCPM 固定视觉压缩、坐标协议，再逐步加入 4／6 件。
4. 另用 PP-OCRv6 small、Xiaomi-OCR-0 比较文字转写；专用 OCR 未覆盖的外观和规则仍由 VLM 完成。照片是否需重拍仍维持 VLM 判断，不能重新引入旧锐度阈值或仅凭 OCR 分数判清晰度。

### 第二轮：真实拍照集

先整理约 50～100 张不同物料、字体和拍摄条件的照片做工程筛选；包含单件、多件、近似字符 `S/5、O/0、B/8`、长型号、允许变化批号、型号错序、Logo 缺失、反光与模糊。人工独立核对原图，不能拿 27B 输出当真值；同一器件的重复裁片／重复拍照不当独立类别。按物料划分调参与验收数据，保留封存集。

逐项统计：

- **误放行**：真实不合格却判合格，单独列数量和反例；另记误拦截。
- **文字**：关键型号整串完全一致率、逐字符错误、允许变化字段是否遵循规则；不要只记字符平均准确率。
- **位置与归属**：漏件、重复计数、元件↔文字↔结论错绑；有人工框后再报 IoU 和器件覆盖率。
- **质量**：模糊漏报、清晰图误要求重拍；明确不合格不能归为“拍摄不清”。
- **规则与协议**：重点／忽略区、现场说明优先级、合法 JSON、完整 Schema／语义通过率、截断及失败。
- **性能**：加载与冷启动、首正文、逐件完成、整张完整结论、p50/p95、峰值 GPU／统一内存；统计成功检验吞吐，不只统计 tokens/s。

50～100 张只是筛选规模；最终可接受的误放行风险和验收样本量由业务目标决定。没有发现错误不等于错误率为零，不能仅凭少量好图宣布“够用了”。

## 8. 复现和资料边界

公开元数据采集不下载权重、不运行推理，联网环境中可执行：

```sh
npm run python -- research/model-selection/collect_small_model_metadata.py --output outputs/small-model-metadata.json
```

本机真实对照需要操作者先确认业务空闲、资源足够，并显式加载候选；脚本本身不会加载／卸载模型，也不会切换默认配置。当前 MLX 案例在 Mac 上使用：

```sh
lms load qwen3.5-4b --identifier sv-survey4b-20261101 --context-length 16384 --parallel 1 --ttl 600 --yes
node research/model-selection/probe_whole_photo.ts --candidate sv-survey4b-20261101 --baseline-template "$HOME/.lmstudio/models/lmstudio-community/Qwen3.8-27B-MLX-4bit/chat_template.jinja" --candidate-template "$HOME/.lmstudio/models/mlx-community/Qwen3.5-4B-4bit/chat_template.jinja" --output outputs/small-model-survey-retry
node research/model-selection/summarize_whole_photo.ts --directory outputs/small-model-survey-retry
lms unload sv-survey4b-20261101
```

Windows 不照抄 `$HOME` 或 MLX 路径；需要对应运行时可加载的模型和实际模板路径。只查看本轮 JSON 不需要重新运行推理；元数据快照可供公司内网离线阅读。网络采集失败会保留错误字段，不把没有访问到的资料写成模型不支持。

本轮更新只包含研究脚本、公开元数据和生成样片实验摘要，没有业务页面／API／数据库迁移，没有下载新模型，没有重新测试所有候选，也没有在 Windows 或目标公司 GPU 上测速度。正式部署前固定具体权重及代码 revision、许可与视觉预处理配置。候选多数为 Apache-2.0，GLM-OCR／Phi／Unlimited-OCR 为本轮元数据列出的 MIT，FastVLM 为 Apple AMLR；以最终使用的具体版本为准。
