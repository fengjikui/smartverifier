# Unlimited-OCR-2 元件丝印独立实测

日期：2026-11-02（北京时间）。本轮实际下载并运行模型，共 7 组、37 次调用，全部在独立环境完成。业务服务、当前千问模型、正品库和检测流程均未改动。

**目前不建议把它作为丝印检测的默认识别后端。** 本机 BF16 社区移植版在默认指令下，多数照片只返回图片块，没有转写丝印。人工单件裁片能改善部分样例，但仍不足以覆盖本轮任务。这个结论适用于下述样片与实现，不能解释成官方 CUDA 版本在所有工业场景的准确率。

可直接打开[图片与模型原文对照页](../../research/unlimited-ocr2/report.html)，展开每项查看输入区域、提示词、完整输出和耗时；[原始结果](../../research/unlimited-ocr2/results-2026-11-02/)及[复现步骤](../../research/unlimited-ocr2/README.md)均已保存。

## 1. 测的是什么版本

| 项目 | 实际设置 |
| --- | --- |
| 官方模型 | `baidu/Unlimited-OCR-2`，提交 `c14071b549f4fcab10909f3c4acc6a2edb366947` |
| 本机权重 | `mlx-community/Unlimited-OCR-2-bf16`，提交 `850d1e483f5a82a0597f0a45aac31b07ba840df2`；BF16，未量化 |
| 规模 | 官方元数据约 3.344B 参数；本轮两个转换后权重文件合计 6,680,172,255 字节，约 6.68 GB |
| 机器 | Apple M2 Ultra、64 GiB，macOS 15.7.4 |
| 运行时 | Python 3.12.13、MLX 0.32.4、mlx-vlm 0.7.11、Transformers 5.22.1 |
| 实际注意力实现 | `DeepseekV2DashModel`；`page_layout=True`，没有退回第一代普通稠密解码器 |
| 默认输入 | `Multi page parsing.`；单图动态分块，全局视图 1024、局部块 640、最多 16 块 |
| 生成设置 | temperature=0；整图 2048 token 上限，裁片 512；单项 120 秒上限；串行 |

Unlimited-OCR-2 的论文重点是长／超长文档解析，通过 SR-SWA 限制每步需要关注的参考量；它的文档榜单成绩不能直接换算成元件丝印准确度。[第二代论文](https://arxiv.org/abs/2610.39308)

官方验证路径使用 NVIDIA CUDA／Transformers，另提供 SGLang 服务方案；本轮采用 Mac 可运行的 MLX 社区转换及原生实现，未执行官方 CUDA 推理循环，也不主张两者逐位等价。原生移植包含 DASH，但仍可能存在预处理或解码差异。[官方模型和推理说明](https://huggingface.co/baidu/Unlimited-OCR-2#inference)、[社区 BF16 权重说明](https://huggingface.co/mlx-community/Unlimited-OCR-2-bf16)

来源、版本、运行时文件哈希见 [provenance.json](../../research/unlimited-ocr2/provenance.json)，两个实际权重的 SHA256 保存在各组结果中。没有为了运行本实验卸载或切换当前 LM Studio 模型。

## 2. 输入和评分口径

复用[9 张样片及人工真值](../../fixtures/inspection/ocr-exploration-v1/manifest.json)，覆盖散放 6 件、透明托盘 30 件、长码双件、18 件混两处差异、清晰参考及两张公开实拍。共 63 次元件出现，其中 60 次主码经过像素核对；另外 3 次 O/0、I/1 等歧义样例按设计／录入声明单列。生成图为 1536×1024，公开实拍沿用原尺寸及[作者许可](../../fixtures/inspection/ocr-exploration-v1/public/ATTRIBUTION.md)。

- **整图**：不提供正品图片、标准答案或比对文字，统计全文中完整主码及重复次数。比如应出现 29 个 `J3` 和 1 个 `J8`，只读出一个 `J3` 不算 30 个都正确。这个指标不证明文字归属于正确元件，不是定位召回率或合格判定准确率。
- **单件裁片**：使用清单中的人工已知粗框，保留原方向、不额外放大，共 16 件；其中 14 件像素核验，2 件声明歧义单列。它测试识字能力，不证明自动定位／分割已可用。
- **转正对照**：选其中 3 个侧向／倒置裁片，按已知角度转正后重测。角度由人工给定，没有用真值挑选模型输出。
- **排字对照**：6 行黑白清晰文字，用于检查链路；不算元件照片正确率。

完整主码严格匹配，不合并 G/6、8/B、O/0、I/1；本批主码均为大写。未识别、错字及截断都不计正确。结果中的 `complete` 仅表示正常停止，空的图片块也可能是 `complete`。所有失败、长重复及解析修正前的评分均保留。

本轮没有公司照片，没有真假物料的业务标签。重复排布、参考图和同一图的裁片不是独立物料；不能据此宣称覆盖 95% 现场场景。

| 人工单件 ROI，14 件可核验 | **4/14** | **2/5** | C01、实拍 358N 主码、18 件图中两处异常读对；全部已标文字行一致为 3/14 |

### 最有价值的对照

同一张 18 件照片，整图输出是图片块列表，例如：

```text
<PAGE><BLOCK>image[48, 121, 160, 320]<FORK>
<BLOCK>image[208, 123, 321, 323]<FORK>
...
```

没有抄出 `QG5S208B`，更没有读出两处异常。不能把“返回 18 个框”解释为“18 件已检验”。这些是文档解析输出的图片块，不是已经验证可用的业务元件定位器。

将同图两处异常按人工粗框分别裁出后：

| 裁片 | 像素主码 | 实际模型文字 | 首字／总耗时 |
| --- | --- | --- | --- |
| C08 | `Q65S208B`，G→6 | `Q65S208B` | 0.315 / 0.521 秒 |
| C17 | `QG5S20BB`，8→B | `QG5S20BB` | 0.348 / 0.562 秒 |

这是两个成功的局部识字例子，说明该实现并非完全无法读取芯片文字；不过其余不少单件裁片依旧不转写，不能据此推导出可直接使用的通用路线。此前 27B VLM 对这两个人工裁片也读对，耗时约 22 秒，但输出还包含比对解释及结构化结论，**不是同等工作量的速度比较**。[上一轮实验与边界](轻量OCR与定位方向探索-2026-11-01.md)

## 4. 提示词诊断

保留默认模式后，额外检查了三种不包含真值的读字指令，没有挑最好提示词替换基线。

| 指令 | 输入 | 结果 |
| --- | --- | --- |
| 普通英文读字指令，要求保留字符、不猜缺字 | 散放、托盘、18 件 | 0/54 次主码；散放和 18 件重复输出，均达到 2048 token 上限，约 22 秒；托盘仍只有图片块 |
| `Free OCR.` | 散放、18 件 | 0/24 次主码，仍只有图片块 |
| `<\|grounding\|>OCR this image.` | 散放、18 件 | 0/24 次主码，两项均重复／异常结构输出，达到 token 上限，约 21 秒 |

后两种不是官方第二代模型卡推荐的默认任务指令，只作兼容性诊断。当前没有证据表明换一个简短提示词就能稳定解决问题。所有诊断原文，包括长重复内容，保存在对应 JSON。

观察到的直接问题是“在做版面／图片块分类，却没有转写物体表面文字”。这与长文档任务和场景文字的差异相符，但本轮没有在官方 CUDA 环境复核，不能把训练目标当作已证实的唯一原因，也不能排除移植及预处理差异。

## 5. 耗时、资源和实际输入

- 1536×1024 整图实际产生 3×2 局部网格，默认输入序列长度 899；两个异常裁片输入长度 279，`spatial_crops=[[1,1]]`。这些值记录在每项 `prepared`，没有仅凭图片文件尺寸猜模型输入。
- 普通整图约 0.8～3.7 秒，但多数没有转写文字，因此**不能把这个速度当作有效识别性能**。正确局部例子的约半秒也只代表这两次暖态读字调用。
- 首次排字调用 10.075 秒，随后的清晰参考为 1.117 秒，存在首调用开销；没有将其拆解为具体算子时间。各独立阶段模型加载约 1～2 秒，下载与加载均不计入推理耗时。
- 最大 MLX 分配峰值约 7.94 GiB；5 秒资源采样的进程 RSS 最大约 6.59 GiB、系统可用内存最低约 7.76 GiB。采样 RSS 不是严格峰值，MLX 与 RSS 口径不同，不能相加，也不意味着整台 8GB 电脑足够运行。
- GPU 分配上限 9 GiB、缓存 128 MiB、CPU 相关线程数 2、串行运行，保留原有服务。运行前及过程中检查系统热状态，未记录到热／性能警告；没有取得芯片温度数值。
- 共 37 次调用，33 次正常停止、4 次达到输出上限；正常停止并不等于正确。没有把截断隐藏成成功，也没有触发内存不足中止。

## 6. 下一步如何取舍

1. **保持生产识别不变**。当前结果不足以让 Unlimited-OCR-2 接管整图丝印或自动放行；空输出不能变成“没有发现差异”。
2. 轻量路线优先继续验证上一轮 PP-OCRv6 small／tiny。它们在同一组照片上已经读出更多有效文字，且权重小得多；但两轮评分归属方式不同，不能把整图计数和逐元件归属指标拼成严格排名。
3. 如果需要继续验证本模型，下一次优先在有 NVIDIA 的机器复核官方单页 `infer`，再决定是否投入文字块裁切、方向处理或微调。先确认运行时一致性，再扩大调参，避免在明显不匹配的输入上投入过多工作。
4. 收集真实照片后，按多件密集／反光托盘／低对比／180°／形近字分组。分别记录全文主码、元件归属、覆盖数量、异常漏读和最终误放行。用公司内网保存真值，不必把敏感照片发出。

本轮实际交付包含模型固定版本、输入哈希、37 次原文及资源记录、评分测试、静态对照和复现脚本；没有把模型接入默认路由，也没有新增业务数据。
