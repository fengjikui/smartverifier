# 平板拍照、一般清晰度与图像数据量

日期：2026-10-17。阶段：官方规格及网页 API 调研、受控降质实验。**尚未拿到目标平板，本轮没有真机摄像头实测。**

## 1. 根据新背景调整验证重点

后续以现场清晰度一般的照片为主要验证对象，覆盖小字、轻微失焦、运动模糊、反光、低对比度、器件占画面比例小等条件。已有清晰合成样例只保留为流程与受控变量基线，不据此确定生产模型、压缩参数或质量门槛。

先做少量可重复的配对实验，观察实际错误；不先为所有可能情况设计复杂处理链。

### 三种拍照路径应分别核对

| 路径 | 能获得什么 | 本项目的处理 |
| --- | --- | --- |
| `<input type="file" accept="image/*" capture="environment">` | 系统相机/文件选择流程交回的图片文件；`capture` 是提示，不承诺特定尺寸 | **当前使用此路径**。以最终 `File` 的真实尺寸、字节数和编码为准 |
| `getUserMedia` + 视频截帧 / `grabFrame` | 视频流当前帧；与相机静态照片的能力不同 | 如以后自建连续取景器，读取实际 track settings 和帧尺寸，避免把预览画面的尺寸当照片尺寸 |
| `ImageCapture.takePhoto()` | 支持时可请求一次独立曝光的图片 Blob，以及期望宽高 | 先探测 API 和 photo capabilities，再核对返回 Blob；不预设 HarmonyOS 浏览器支持完整能力 |

依据：[capture 属性](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/capture)、[getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)、[grabFrame](https://developer.mozilla.org/en-US/docs/Web/API/ImageCapture/grabFrame)、[takePhoto](https://developer.mozilla.org/en-US/docs/Web/API/ImageCapture/takePhoto)。流式相机还要求安全上下文；局域网普通 HTTP 访问和本机 localhost 的权限条件不相同，见 getUserMedia 文档。

### 当前代码核对

- `web/src/App.tsx`：使用文件输入调用后置相机，拍照/相册文件放进 `FormData`；当前没有用 canvas 截取视频，也没有在上传前重编码照片。
- `web/src/api.ts`：读取图片解码后的 `naturalWidth/naturalHeight`。横竖方向调换可能来自 EXIF，不等于丢像素。
- `server/service.ts`：按收到的字节保存原图，记录哈希和尺寸，单图上限 20 MiB。

这些是当前源码证据；平板系统相机、浏览器、相册流程本身是否改写图片，仍需实际拍摄对照。

## 4. EXP-005：降质、编码与画幅的受控实验

### 方法

本机 M2 Ultra / 64 GiB，完整视觉版 Qwen3.5-4B MLX 4bit，上下文 8192，并行 1，温度 0，关闭思考，每轮 55 秒时限，轮间休息 3 秒。共七个条件，每种一次，仍是相同四个不同的合成元件。

使用同一张 960×960 四件白板构造 JPEG 编码、模糊与缩小条件；另外把相同 430×430 原裁片放到 4160×3120 的白色画布，模拟“大画幅但元件占比小”的情况。**这是算法构造的模拟，不是平板照片，也不能等价于真实失焦、反光和运动模糊。**

JPEG 实验固定 Pillow 编码器、`subsampling=0`。为复用现有受限 SDK，JPEG 候选先解码成无损 PNG 再发送，测试的是 JPEG 带来的视觉损失；表内候选文件体积不是实际 SDK PNG 的上传字节数。结果 JSON 同时保留两种字节数，未声称验证了 JPEG 直接上传链路。

### 结果

| 条件 | 输入像素 | 候选文件体积 | 全文离线核对 | 输出结构符合约定 | 本轮耗时 |
| --- | --- | --- | --- | --- | --- |
| 清晰 PNG 白板 | 960×960 | 1168.3 KiB | 4/4 | 是 | 3.089 秒 |
| 同像素 JPEG quality 85 | 960×960 | 164.9 KiB | 4/4 | 是 | 2.959 秒 |
| 同像素 JPEG quality 60 | 960×960 | 99.9 KiB | 4/4 | 是 | 2.941 秒 |
| 高斯模糊半径 1.2，再 JPEG85 | 960×960 | 113.5 KiB | 4/4 | 是 | 2.963 秒 |
| 高斯模糊半径 3，再 JPEG85 | 960×960 | 78.4 KiB | 4/4 | **否：返回数组** | 2.394 秒 |
| 缩到 320，再 JPEG85 | 320×320 | 25.3 KiB | 4/4 | 是 | 1.924 秒 |
| 大画幅、小占比 | 4160×3120 | 1319.0 KiB（PNG） | 4/4 | **否：返回数组** | 6.468 秒 |

结构不符的两次返回了合法 JSON 数组，而非要求的 `{"items":[...]}`。单独核对文字都正确，不把这两次标为完整接口成功；模型原文保留，没有重试补答。

### 能得出的结论

- 在本组短、可读且重复模式较多的字样中，JPEG85 候选文件比 PNG 小约 85.9%，文字仍读对；不能据此认定 JPEG85 对其他字样、颜色和细微图案都无损。
- 同像素 JPEG 主要减小文件字节数，通常不会同比减少视觉 token。文件小与模型输入像素少是两种不同优化。
- 模拟 13 MP 画幅的文字也读对了，但耗时高于紧凑裁片。本次输出排版长度不同，不能把时间差完全归因于背景或预填充，也不能据一次实验宣称稳定加速比。
- 320 图与模糊图能读对，**不表示**实拍小字都可以缩到该尺寸。本组未测长字符串、磨损、低对比度与反光，也没有真实“需重拍”标签，不能据此确定质量判定阈值。
- 先前已出现过长条拼图缩小后漏读差异的反例，详见[批量机制研究](模型图片预处理与批量识别调研-2026-10-17.md)。仍应限制布局，并做实拍配对验证。

## 5. 建议的第一版处理规则

```text
接收图片文件，读取真实尺寸 / 字节数 / 编码
  → 保留收到的原始字节
  → 正确解码 EXIF 方向，从原分辨率定位元件
  → 保留外形、引脚与适量边距，直接裁出元件
  → 评估各裁片可读性及送入模型后的预期尺寸
  → 有必要才做一次缩放或重编码，组成小批量
  → 按真实模型输出和人工真值验证
```

### 优先避免的损失

不要先按“所有图片最长边 1280 / 每张必须小于几百 KB”之类全局规则缩整图，再从缩小图裁件。按已核验的本机 2048 上限推算，4160×3120 整图会先约缩为 2048×1536，线性尺寸约剩 49.2%；原本 40 像素高的字会约剩 20 像素。先裁片可以让有限视觉预算更多用于器件。

13 MP、JPG 体积、丝印可读性并不一一对应。白色背景的 PNG 可以很小却占很多像素；大图也可能因为失焦或器件太小而无法读字。无需为了统一尺寸强制放大所有裁片。

### 原图、预览和模型输入分别处理

- **证据原图**：原样保存，作为复检依据。当前收到的若已是 JPEG，优先避免无必要的 JPEG 再编码。
- **界面预览**：可单独生成较小缩略图，减少平板解码和滚动开销；点击详情时再读原图/清晰裁片。
- **模型裁片**：从原分辨率生成；根据实际模型预算决定是否缩放。JPEG、PNG 的选择要用目标文字和外观特征验证，不能只比较肉眼整体观感。

目前先不固定统一 JPEG 质量值、最大裁片尺寸或清晰度分数。可以记录元件占比、文字像素高度、反光和模糊指标作辅助，再用模型实际结果与人工判断校准。单纯的全图锐度分数可能被清晰背景干扰，不能独自决定是否可检。

照片低到无法可靠判断时，标记需要重拍，并按已有规则阻止未完成任务提交；不把拍摄问题当作元件不合格。重拍替换原记录，避免重复统计。

## 6. 拿到平板后的短实验

1. 记录设备具体型号、系统、浏览器版本；分别用系统相机、网页拍照入口、相册添加同一原图。
2. 每次记录实际编码尺寸和解码尺寸、文件字节数、格式、方向及服务端哈希。先确认网页是否额外降采样，再讨论优化。
3. 同一组真实元件分别拍 1 / 4 / 6 / 8 件，在正常和一般照明、正常和轻微抖动下取少量样本；人工逐字核对，标注哪些确实无法判读。
4. 对同一原图做配对：原图直接识别、原分辨率裁片、裁片 JPEG85/其他候选、先缩整图后裁片。分别观察文字/图案差异、误放行、需重拍率、上传大小和耗时。
5. 只在发现明确收益后固定参数；出现失败则保留样本和失败原因，继续归档。

这一步优先解决“实际能拍到什么、哪些处理会影响识别”，暂不扩展为复杂的自动增强系统。
