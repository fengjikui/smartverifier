# 前置分离与批量识别接口设计 v0.1

日期：2026-10-17。协议：`sv.vision.v1`。

**本文记录2026-10-17的批量接口合同、分批规划、输入／输出校验及测试。2026-10-18已另行通过 `VisionPipeline` 接入OpenCV分离和LM Studio双图逐件识别，复用本合同的几何与JSON校验；批量计划、预算预检及白板批量送模尚未启用。当前运行方式见[真实识别试用与部署](VLM配置.md)。**

## 1. 设计依据与结论

先按用户提出的假定设计：批量识别可以成立，候选配置支持每批最多 4 张待检图片，或一张拼图最多放 6 个元件。这是待实拍验证的能力假设，不是已完成的准确率验收。

用户已于 2026-10-17 确认：**前置分离器以元件定位、裁剪为主，结合既有要求进行旋转摆正；模型分流仅预留扩展接口，本阶段不启用。**

核心流程：

```text
原始照片 → 纠正 EXIF 方向 → 分离元件 → 质量／覆盖检查
    → 可选的模型分流 → 分批 → 独立传图或生成白板拼图
    → 运行时预算检查 → 识别 → 严格校验 → 按元件写回结果
    → 沿用已有汇总和提交门槛 → 人员点击提交丝印项到 MES
```

前端继续负责拍照、预览、检测进度、可选核对与提交。定位、裁剪、分批不要求检验员手动操作。接口拆分是代码职责边界，首轮不必部署为多个微服务。

### 三种数量分别计数

| 数量 | 含义 | 候选规则 |
| --- | --- | --- |
| 原始照片数 | 检验员拍了几张照片 | 不因批量上限而限制整个任务 |
| 元件数 | 实际发现并独立判定的元件个数 | 每模型批次最多 6 件；不良数也按件统计 |
| 模型输入图片数 | 参考图 + 待检裁片或拼图 | 候选每批最多 4 张待检图 + 1 张参考图，共 5 张 |

例如，一张原图拍到 6 个元件，可以裁出 6 张图，独立传图模式分为 **4＋2**；拼图模式可组成 **1 张包含 6 件的待检图，加 1 张参考图**。多张原图各拍一件也能组成同样的模型批次，且每件仍可追溯到自己的原图。

若实际部署的限制是“总共只能输入 4 张图”，将 `maxTotalImages` 设为 4；预留一张参考图后，独立传图模式自然变成 **3＋3**。模型批次和业务任务分开：内部可以多批处理，任务仍不允许部分提交。

## 2. 模块与接口

代码目录：`server/vision/`。正式类型与字段校验以 `contracts.ts` 为准。

| 接口／函数 | 输入 | 输出／职责 |
| --- | --- | --- |
| `ComponentSeparator.separate` | `PhotoInput`，取消信号 | 元件位置、裁片、反向坐标映射、质量提示、覆盖状态；不输出合格／不合格 |
| `ComponentRouter.route`（可选） | 元件列表、任务依据版本、取消信号 | 每个元件使用的模型能力配置与理由；不改变元件身份 |
| `planBatches` | 同一依据、同一能力配置的一组元件、布局、预算估算器 | 批次计划，以及不能进入识别的元件和原因 |
| `ContactSheetComposer.compose` | 一份拼图批次计划、取消信号 | 实际拼图资产、每件位置和图内短标签 |
| `prepareRecognitionRequest` | 批次、检测依据、可选拼图产物 | 核对布局后生成可发送的图片列表 |
| `RecognitionAdapter.capabilities` | 无 | 当前模型／部署支持的图片、元件、尺寸与预算上限 |
| `RecognitionAdapter.preflight` | 识别请求、取消信号 | 执行前检查图片处理及上下文预算；不合适就明确拒绝 |
| `RecognitionAdapter.recognize` | 同一识别请求、取消信号 | 严格结构化结果、原始响应引用、模型及输入尺寸记录 |
| `validateSeparation` / `validateExecution` | 当前输入版本、返回内容 | 拒绝过期、漏项、重号、错误结构；校验后才能写回业务结果 |

分离器可以先接简单背景下的 OpenCV 方法，之后替换为检测／分割模型，或者按物料选择算法。若不能可靠定位或疑似漏件，返回明确问题，不能把“没找到”当成“全部合格”。`coverage: complete` 是算法声明，合同只能检查自洽性，真实漏检率仍必须通过样本验证。

模型分流可在以后采用“小模型处理普通件、大模型处理复杂件”的策略。目前只留接口，不自动启用，也不把未分类件当成简单件。协调器必须校验分流结果一件一条、无漏项／重复，且所用能力配置已注册，然后分组调用规划器。低置信度升级重跑等策略另行实验，不能擅自变成强制人工复核。

## 3. 原图、坐标、元件身份

### 图片资产

所有接口用 `ImageAsset` 引用图片：

```ts
type ImageAsset = {
  assetId: string;
  sha256: string;
  mime: 'image/jpeg' | 'image/png' | 'image/webp';
  width: number;
  height: number;
  bytes: number;
};
```

原图按上传文件原样保留，不覆盖重编码。另存方向纠正后的全分辨率图和模型裁片。资产服务负责验证文件实际尺寸、哈希及访问权限；合同中的元数据不能取代文件校验。Worker 通过受控资产解析器读取文件，不接收模型提供的任意路径或外部 URL。

`PhotoInput` 包括 `photoId`、`photoVersion`、`original`、`upright` 和 `originalToUpright`。方向纠正图没有方向变化时可以与原图共享资产引用、使用单位矩阵。

### 元件定位

`PreparedComponent` 的主要字段：

| 字段 | 约定 |
| --- | --- |
| `componentId` | 服务端分配的稳定身份，用来匹配结果；不依赖模型返回顺序 |
| `photoId / photoVersion / sourceSha256` | 绑定来源照片及具体版本 |
| `quadPx` | 方向纠正后的全分辨率原图中的四角，沿边界顺序排列；像素坐标，左上为原点，x 向右、y 向下 |
| `modelView` | 实际送模型的裁片资产，保留文字与适量周边区域 |
| `viewToUprightOriginal` | 3×3 行优先齐次变换矩阵，从裁片坐标映射回方向纠正后的原图 |
| `rotationClockwiseDegrees` | 生成裁片时记录的顺时针旋转角度，范围 -180～180；不是让调用方再次旋转 |
| `quality` | `usable`、`undetermined` 或 `needs_recapture`，以及原因 |
| `routeHint` | `unclassified / standard / complex`；只是分流提示 |

齐次矩阵应用于列向量 `[x,y,1]`，变换后除以第三个坐标。其逆矩阵可以将原图位置投到裁片。已有前端的归一化 `bbox` 可由原图四角在渲染时换算，暂不修改已保存的数据格式。

分离器可在降采样副本上做检测，但输出位置必须还原到全分辨率图，并从全分辨率图裁片。旋转／透视矫正会插值，不能称为数学无损；尽量合并为一次几何变换，记录处理版本，不使用会臆造丝印笔画的生成式修复。不能确定字向时保留问题信息，不凭空改字。

相同像素哈希不等于同一元件，不能据此合并计数。重试、重新拼图、修改检测说明时复用已有元件身份和裁片；重拍替换对应原照片、使旧输入失效，不把旧照片与新照片双重计数。如果替换的是含多件的照片，按整张照片重建该组定位，不默认猜测新旧元件的一一对应关系。

### 分离状态

`SeparationResult` 同时包含 `status`、`coverage`、元件数组及 `issues`：

- `completed + complete`：定位完成，至少有一件；仍需检查每件质量，不代表已检测合格。
- `recapture_required`：照片无法可靠处理，提示重拍。
- `failed`：算法／运行异常，保留技术错误，允许有界重试或更换处理器。
- `coverage: uncertain`：疑似存在未处理区域；禁止将这张照片标成完整完成。

若部分元件可读，可先产生这些元件的结果，但原照片的未完成／重拍状态必须保留，直到解决前不能提交整个任务。检测质量的具体阈值、采用传统规则还是小模型，不在本合同中写死。

## 4. 分批与白板拼图

当前 `candidateProfile` 是可测试的候选配置：

```json
{
  "profileId": "candidate-vlm",
  "profileVersion": "v1-assumed",
  "adapterId": "not-connected",
  "mode": "mock",
  "layouts": ["separate_images", "contact_sheet"],
  "limits": {
    "maxSampleImages": 4,
    "maxComponents": 6,
    "maxTotalImages": 5,
    "maxImageLongEdge": 2048,
    "maxImagePixels": 4194304,
    "maxEstimatedVisualTokens": 6144
  }
}
```

这些尺寸／预算是当前研究基础上的**规划默认值**。新模型、量化版本、推理引擎或预处理设置变化，均需生成新的能力配置版本并验证。`mode: mock` 与 `not-connected` 明确表示没有真实适配器接入。

规划器按输入顺序贪心分组，不追求最优装箱。遇到数量、尺寸或预算限制时拆批；单件仍超限则返回 `blocked`，不得静默缩小或丢件。参考图也要先按明确策略生成模型视图并计入预算。原图、参考图的原始资产保留在业务快照中，不因模型视图调整而丢失。

拼图方案：白底、适度间隔、优先接近方形，避免很长的横条。v1 排版只平移、不缩放裁片；标签使用 `C01` 等短名，放在裁片上方的独立区域，并保存短名与 `componentId` 的映射。模型仍必须返回真正的 `componentId`，不能只返回短名或数组序号。

布局计划包括整图尺寸、各裁片位置、标签、`scale: 1`。生成器返回的图片尺寸和布局必须与计划完全一致，否则拒绝发送。为避免背景误导，保留元件自身颜色；白底仅填空白处，不覆盖元件像素。实际生成器仍需图像测试验证，布局合同本身不证明像素已正确贴合。

视觉 Token 估算器可替换。提供的 `qwenPatch32Estimate` 只是当前千问 32 像素网格和小图放大机制的近似值，不能泛用于所有模型。估算包含参考图、拼图留白；执行前还要由适配器检查**模型内部实际尺寸、完整提示词、多图开销及输出预留**，不能只看 HTTP 返回的 `prompt_tokens`。负载升高时优先排队或减小批次，不能偷偷降低丝印分辨率。

## 5. 识别请求与响应

### 请求组成

`RecognitionRequest` 包括：

1. `batch`：任务／轮次／快照、批次与尝试 ID、依据指纹、能力版本、元件映射、布局及预算。
2. `basis`：正品模型视图、标准说明、现场说明、提示词版本；优先级固定为 `onsite_over_standard`。
3. `sampleImages`：实际待检图片引用；顺序为各元件裁片，或唯一的一张实际拼图。发送给模型时，参考图在第 0 位，其后是这些待检图。

分批时为参考图、两类说明、提示词版本和优先级生成 `basisSha256`；准备请求时再次核对，避免分批后换了说明或图片却沿用旧计划。协调器需从可信、不可变的快照读取依据，不允许客户端伪造标准版本。

适配器负责把合同转成 LM Studio 或未来推理服务的请求格式，注入每件身份／图片位置、识别规则及严格输出 Schema。模型不负责统计整个任务是否可提交，也不调用 MES。

### 模型只返回检测内容

以下示例对应一个二元件批次：

```json
{
  "items": [
    {
      "componentId": "c1",
      "status": "decided",
      "verdict": "PASS",
      "lines": ["SV358", "A2609"],
      "confidence": 0.96,
      "reason": "丝印与正品一致，日期码按说明允许变化",
      "features": ["圆点定位标记位于左上角"],
      "differences": []
    },
    {
      "componentId": "c2",
      "status": "decided",
      "verdict": "FAIL",
      "lines": ["SV385", "A2609"],
      "confidence": 0.93,
      "reason": "型号末尾数字顺序不同",
      "features": [],
      "differences": [
        {
          "category": "text",
          "message": "第一行末两位顺序不同",
          "lineIndex": 0,
          "referenceText": "SV358",
          "sampleText": "SV385"
        }
      ]
    }
  ],
  "instructionConflicts": []
}
```

`lineIndex` 从 0 开始。文字差异仅是证据；是否允许某段变化，要结合标准与现场说明，不能用字符串不同直接覆盖模型依规则给出的结论。逐字红色对齐沿用业务层的文字对照功能。

看不清时，单件返回 `status: unreadable, verdict: null`，写明原因；不把它转换为不合格，也不上传 MES 的“不确定”枚举。暂按重拍处理。置信度为 0～1，不能可靠提供时为 `null`，界面显示“未提供”；自报置信度尚未经校准，不是准确率承诺。有明确结论但把握低时提示即可，人工复核仍为可选。

校验要求：严格 JSON 根对象；每个输入元件恰好一条结果；支持乱序但必须按 ID 对应；漏项、重号、额外 ID、无效结论、格式错误均拒绝本批次入账。保留原始响应后可有界重试；不默默把根数组包装为“成功对象”。响应错误是技术错误，不是产品不合格。批次失败不会抹掉此前其他已完成批次，但会阻止任务部分提交。

### 执行元数据由适配器补充

`RecognitionExecution` 包含协议、批次、尝试、快照、适配器、实际模型、能力配置版本、预处理版本、耗时、原始响应资产及 `reply`。这些身份字段由服务端适配器填写，不信任模型自己宣称的任务身份。

`inputMetrics` 按参考图与待检图的发送顺序，记录 `inputIndex / assetId / sentWidth / sentHeight / effectiveWidth / effectiveHeight`。发出的图与合同尺寸必须一致。推理引擎内部最终尺寸只有实际取到时才填；不知道就将两个 `effective` 字段都填 `null`，不能把发送尺寸冒充内部尺寸。若内部预处理变化，适配器应更新能力配置或拒绝执行，不能悄悄沿用旧假定。

## 6. 快照、增量与失败处理

业务协调器后续接入时需持久化输入快照：任务、轮次、正品版本、说明版本、选中原图的 ID／版本／哈希、分离器／预处理／提示词版本、裁片与能力配置、批次计划。`snapshotId` 绑定这些不可变输入。

**不能直接把现有 `Round.revision` 当作模型输入版本**：该值也随进度更新。输入有效性单独检查，否则第二个元件结果会因第一个元件更新了进度而错误失效。

| 变化／异常 | 行为 |
| --- | --- |
| 新增照片 | 为新增部分建立工作快照；不使已完成的旧照片结果失效，也不无故取消仍有效的旧工作 |
| 替换／删除照片 | 使涉及该照片的未完成批次失效；旧结果保留历史，不参与当前计数 |
| 修改现场说明 | 所有已有元件按新依据重新判定，照片／定位资产可复用；旧结果及人工修改留历史 |
| 管理员更新正品 | 当前轮次先使用已固定的标准快照；是否切换由明确操作发起，不能处理中途悄悄更换 |
| 超时／可重试服务异常 | 同一逻辑批次、同一输入，生成新 `attemptId`，记录尝试次数；采用有上限的退避，不无限重试 |
| 结果迟到 | 写入前核对当前仍有效的输入、批次、尝试和能力版本；旧尝试拒绝写回 |
| 用户取消／旧输入失效 | 传递 `AbortSignal`；即使底层不能及时取消，也不允许迟到结果覆盖当前结果 |
| 缺少正品 | 进入检测前阻止，提示联系管理员 |
| 拼图／预算错误 | 拆批、显式重做模型视图或改配置；单件仍不满足则报技术问题，不输出伪结论 |

`validateExecution` 提供当前作用域核对，但**不能替代数据库事务**。协调器必须在原子写入中核实该批次照片仍在本轮、来源版本未变、尝试仍有效，再应用已校验结果；同一成功尝试重复回调应返回原回执，不重复累计。

`currentScope` 指该输入快照此刻是否仍有效，不是“整个任务唯一的最新工作 ID”。后续追加照片可以有新快照，而旧照片的有效快照仍可完成。若一个批次中有照片被删除／替换，整批迟到结果拒绝写入，再为仍需识别的元件重建计划。

进度先显示“正在定位元件”，此时总件数可以未知；定位完成后显示完成件数／总件数以及排队、识别、需重拍、失败。模型单次请求处理中使用不确定进度提示，不按计时伪造识别百分比。一个批次返回后可一次更新多件的结果。

任务汇总继续按当前业务规则：按元件计数；任一有效元件不合格则整体不合格；存在质量、未完成、技术错误或过期结果时均不能提交。保留 AI 原判与人工修正历史；模型输出不覆盖人工审计。MES 回填仍是人员发起的独立动作，与推理重试分开处理。

## 7. 前端 API 与可选 Worker HTTP 形式

前端可继续使用现有：

```text
POST /api/rounds/:id/analyze    → 202，异步执行
GET  /api/tasks/:id            → 当前任务、轮次、进度与元件结果
```

接入真实实现时再扩展进度字段，保持拍照、检测、提交这条路径稳定。模型批量大小不暴露为现场操作步骤。

若分离器用 Python、识别用独立推理服务，可将内部函数合同映射为以下 Worker API；**下表只是设计，当前服务器没有提供这些路径**：

| 拟定内部接口 | 请求体 → 响应体 |
| --- | --- |
| `POST /internal/vision/v1/separate` | `PhotoInput → SeparationResult` |
| `POST /internal/vision/v1/route`（可选） | `{components, scope} → {assignments}` |
| `POST /internal/vision/v1/compose` | `PlannedBatch → ComposedSheet` |
| `GET /internal/vision/v1/profiles/:id` | 当前可用 `ModelProfile` |
| `POST /internal/vision/v1/preflight` | `RecognitionRequest → {accepted, reason, estimatedTotalInputTokens}` |
| `POST /internal/vision/v1/recognize` | `RecognitionRequest → RecognitionExecution` |

单个 Worker 请求可以有超时地同步返回；平板面对的是业务服务的异步任务，不用一直保持一个推理连接。首轮每个模型执行队列并发为 1，图片处理也设保守上限；以后按实际硬件增加并发，不把几十个平板等同于几十个模型同时执行。

Worker 仅允许业务服务调用，鉴权与受控文件访问放在传输适配层；服务端验证身份、任务权限和标准归属。连接中断时向下传递取消，返回结构化技术错误并标注是否可重试。仅启动本机服务时可采用本地调用，无须为这次接口设计新增公网服务。
