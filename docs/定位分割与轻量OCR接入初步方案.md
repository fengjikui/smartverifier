# 定位分割与轻量 OCR 接入初步方案

日期：2026-10-31。用途：与算法同事对齐交付边界及第一轮联调方式。

**本文是接入计划，不代表分割模型或 OCR 已接通。当前默认仍是整张照片交给 VLM。建议同事先交付可独立运行的算法模块，由本系统增加适配层，不需要他重写前端、正品管理或 MES 流程。**

## 1. 先接什么，暂时不改什么

建议分三步，每一步都与当前整图 VLM 使用同一组照片对照。

| 阶段 | 新增能力 | 对正式检测结果的影响 |
| --- | --- | --- |
| A：旁路试验 | 对原图做定位、裁剪、转正和 OCR，保存原图、标记图、裁片及读文 | 不写入正式结论；检验仍走现有 VLM |
| B：裁片＋VLM | 定位可靠时，逐件裁片与正品图片交给现有 VLM 比对 | 由 VLM 判断清晰度和合格／不合格；保留原图回退 |
| C：OCR 辅助 | OCR 先读文字，再把原始读文作为辅助证据交给 VLM；也可先只在后台对照 | 验证后再启用；不能因为 OCR 字符串相同就自动判合格 |

首轮不做纯 OCR 自动放行、不重新启用旧 OpenCV 裁剪、不默认启用白板批量识别。OCR 可读文字不等于已检查 Logo、图案、字体、封装和允许差异；OCR 也不一定支持自然语言检测说明。

**清晰度继续只由 VLM 判定。**分割器的低检测分数、OCR 低分、空读文或算法超时，只能记录为算法问题／辅助证据不足，不能直接生成“照片模糊，请重拍”。算法运行失败与真实图片不可判读是两件事。

## 2. 现有代码可以复用到哪里

| 位置 | 已有内容 | 接入时的动作 |
| --- | --- | --- |
| [contracts.ts](../server/vision/contracts.ts) | `ComponentSeparator`、`PhotoInput`、`SeparationResult`、裁片和坐标合同；另有分批识别合同 | 分离器适配这些类型，不另造一套业务照片与元件身份 |
| [validation.ts](../server/vision/validation.ts) | 版本／哈希、四角、矩阵、漏项／重号等校验 | 写入业务结果前调用；仍需另做实际文件、像素和映射一致性检查 |
| [local-pipeline.ts](../server/vision/local-pipeline.ts) | 当前实际 `VisionPipeline`；整图 `recognizePhoto`，以及预留的 `prepare`／逐件 `recognize` | 增加可选编排适配器，保留当前整图实现 |
| [service.ts](../server/service.ts) | 队列、逐照片／元件写回、增量识别、重判、人工修正、汇总和提交门槛 | 串接新编排，保持业务规则 |
| [batching.ts](../server/vision/batching.ts)、[preparation.ts](../server/vision/preparation.ts) | 分批及拼图布局／引用核对 | 属于预留能力，当前主流程未调用；首轮不必接入 |
| [reference-scope.ts](../server/vision/reference-scope.ts) | 正品重点区／忽略区及说明 | 保留其位置含义，不能被 OCR 的全文匹配替代 |
| [python-runtime.ts](../server/python-runtime.ts) | 跨平台解释器选择、UTF-8、保守线程配置 | 本机 Python 调用复用；不同模型依赖可用独立环境 |

### 不能忽略的实际接线工作

现有合同不是一个已经运行的分割 HTTP 服务，也不是把模型地址填进配置就能启用：

- `service.ts` **优先调用存在的 `recognizePhoto`**。只改 `prepare()` 增加裁片，仍会走整图分支。新编排需要明确选择路径；可以实现一个新的 `VisionPipeline`，暂不提供 `recognizePhoto`，使用逐件分支，也可以扩展整图分支显式调度。首轮推荐前一种，减少改动范围。
- `Photo` 当前没有独立的 `photoVersion`，而分离合同需要。需增加版本管理／映射：新照片从 1 开始，沿用同一照片 ID 替换内容时递增；同时核对原图哈希。不能把每次进度变化都会增加的轮次 `revision` 当成照片版本。
- `PreparedComponent` 不能直接塞进前端的 `ComponentResult`。适配器需要保存裁片资产，建立业务元件 ID 映射，并生成归一化 `bbox`、显示标签及 `crop` 引用。
- 管理端默认分析器和本机调试入口当前使用 `instanceof LocalVisionPipeline` 判断。换成组合适配器时，需显式注入原有 `referenceAnalyzer`，并适配调试入口，或先抽出能力接口；不能导致正品自动分析或调试入口悄悄失效。
- 前端来源类型当前只有 VLM／兼容旧 LM Studio，不能把独立 OCR 结果伪装为 VLM 合格结论。首轮把 OCR 保存为独立辅助证据；若将来允许 OCR 独立判定，需另改来源类型、报告和业务规则并验收。

## 3. 定位／分割模块的输入输出

### 输入复用 `PhotoInput`

| 字段 | 作用 |
| --- | --- |
| `photoId`、`photoVersion` | 来源照片与版本 |
| `original` | 原始资产：ID、SHA-256、格式、尺寸及字节数 |
| `upright` | 正确处理 EXIF 方向后的全分辨率图；无方向变化时可引用同一资产 |
| `originalToUpright` | 原始像素坐标到方向纠正图的 3×3 变换矩阵 |

算法可在小尺寸副本上检测，但返回位置必须还原到方向纠正后的全分辨率图，并从全分辨率图裁片。不得拿浏览器缩略图做正式 OCR。图片交由服务端受控解析；同事的核心算法可以读服务端传入的图片，不必了解账号、任务和数据库。

### 输出复用 `SeparationResult`

顶层包含 `protocol: "sv.vision.v1"`、来源照片／版本／哈希、分离器和处理版本、`status`、`coverage`、`components`、`issues`。完整结构以代码为准。

每个元件至少需要：

| 字段 | 必须约定清楚的内容 |
| --- | --- |
| `componentId` | 系统适配层分配并持久化业务身份；算法临时编号要建立对应表，不能按返回数组位置写回 |
| `quadPx` | 方向纠正图中的四角，沿边界排列；单位为像素，原点左上、x 向右、y 向下 |
| `modelView` | 实际裁片资产及哈希、尺寸、字节数 |
| `viewToUprightOriginal` | 裁片坐标映射回方向纠正图的 3×3 行优先齐次矩阵；作用于列向量 `[x,y,1]` |
| `rotationClockwiseDegrees` | 已经生成裁片时采用的顺时针角度，不是要求系统再次旋转；范围 -180～180 |
| `quality` | 算法阶段先用 `undetermined`，由后续 VLM 判断可读性；现有规划器允许该状态继续识别 |
| `routeHint` | 首轮用 `unclassified`，不据此自动认为元件简单、可以由 OCR 放行 |

检测框、旋转框通常足够首轮裁剪，不强制要求像素级掩膜。如果有掩膜，可单独交付作为扩展证据，不能擅自在严格 v1 JSON 中加字段。首轮优先保留矩形内真实背景，不把元件边缘、引脚或丝印笔画抠掉。

裁片应包含整个元件及适当留白；文字方向不确定时可保留原方向或记录候选，不把长边方向等同于文字方向。避免多次缩放、旋转插值；不用生成式超分辨率补字，不覆盖原图。

`coverage` 表示有没有可靠覆盖整张照片的全部元件，不是置信分数超过阈值就必然完整。零元件、疑似漏件、粘连拆分不可靠时不能返回“完整成功”。现有 `validateSeparation` 会拒绝 `completed + uncertain` 或完整但零元件；疑似不完整应使用非完成状态并附问题，转入原图回退或技术待处理。

## 4. 小 OCR 的最小交付合同（拟新增）

**以下字段尚未实现，首轮对齐后再补运行时 Schema。**OCR 负责转写及位置，不负责业务合格结论；也不要求它接收 VLM 的自然语言提示词。

```ts
type OcrRequest = {
  requestId: string;
  componentId: string;
  photoId: string;
  photoVersion: number;
  sourceSha256: string; // 来源原照片
  image: ImageAsset;   // 本次真正输入的裁片
};

type OcrResult = {
  requestId: string;
  componentId: string;
  photoId: string;
  photoVersion: number;
  sourceSha256: string;
  inputSha256: string; // 裁片哈希，须与 image.sha256 一致
  state: 'completed' | 'failed';
  lines: {
    text: string;
    quadPx: [[number, number], [number, number],
             [number, number], [number, number]]; // 本次输入裁片坐标
    score: number | null;
  }[];
  engine: string;
  modelVersion: string;
  preprocessingVersion: string;
  scoreMeaning: string; // 明确量纲／范围；不称为已校准正确率
  elapsedMs: number;
  warnings: string[];
  error: { code: string; message: string } | null;
};
```

`ImageAsset` 引用已有合同。未知分数返回 `null`，不编造 0.99；空读文可以是 `completed + lines: []`，只表示这次未读到文字，不等于合格或模糊。失败时 `error` 非空，不能用空成功结果掩盖故障。文字框至少按行提供；字符级位置、候选字及方向分数可在下一版扩展，首轮不强制。

必须保留 OCR 原始结果、换行、大小写、前导零及标点。不要根据正品把待检 `5` 改成 `S`，也不要把易混字符统一后再宣布一致；文本规范化可以另存用于展示，但不能覆盖原始证据。

重点／忽略框画在**正品图**上，不能直接把同样的归一化坐标套到样品裁片；两张图的摆放和比例可能不同。首轮仍由 VLM 看正品图、样品裁片和范围说明确定对应位置。需比对的文字只保留规定范围，忽略同一位置的变化，不全局删除其他位置相同字符串。

## 5. 同事怎么封装，我们怎么接

同事先提供离线入口即可：输入一张图，输出结果 JSON、裁片和带框预览。JSON 按 UTF-8，日志走 stderr，结果走 stdout 或明确的结果文件，不把日志混进 JSON。

正式联调建议模型常驻，避免每张照片都重新加载权重。两种方式任选其一：

| 方式 | 同事提供 | 本系统适配 |
| --- | --- | --- |
| 同机 Python 模块／常驻 Worker | 初始化、`separate(image)`／`ocr(image)`、版本信息、退出清理 | Node 通过受控进程协议调用，解析为上述合同，管理排队／超时／取消 |
| 独立算法服务 | 受控上传或字节输入、健康检查、请求 ID、明确的成功／失败响应 | 服务端 HTTP 客户端转发，地址／超时／认证可配置；浏览器不直连模型 |

HTTP 路径与鉴权等到选定交付方式后约定，当前没有已经可调用的分割／OCR API。跨机器时不能只传开发电脑本地路径或系统内部 `assetId`，需传图片字节或采用经过约定的受控资产传输；本地路径只允许同机适配层解析。

同事可使用自己的原生模型输出格式，**由适配层统一字段与坐标**，不要求把业务逻辑写进模型仓库。若同时返回裁片与变换矩阵，必须有自动对照：裁片四角映射回原图后，与返回定位位置一致。

部署材料需包含 Python 版本、锁定的依赖、权重取得方式与校验值、CPU／GPU 支持范围、模型使用许可、启动及健康检查方式。算法依赖与当前轻量基础依赖分开，先用独立环境；不要为试一个模型直接升级整个业务环境。Windows 不依赖 `.venv/bin/activate`，调用具体解释器，文本统一 UTF-8；使用 PyTorch 等运行时时也需单独限制线程和并发。

## 6. 本系统需增加的编排与配置

首轮编排：原图保存 → 分离 → 文件／版本／坐标校验 → 可选 OCR → 裁片＋原正品图交给 VLM → 逐件写回 → 现有汇总与人工可选修正。

分离超时、失败或覆盖不确定时，丢弃该次局部判定，回退到**完整原图 VLM**。只有回退也取得全图完整结果后，照片才能完成；若仍无法判读或覆盖不确定，就保持待处理／需重拍。不能只提交成功识别到的部分。OCR 不可用时可跳过辅助读文继续 VLM，并记录降级原因。

拟新增以下配置；**尚未实现，当前设置这些名字不会生效**：

```dotenv
SV_VISION_PIPELINE=original-vlm
# 候选：original-vlm / separated-vlm
SV_SEPARATOR_PROVIDER=off
SV_SEPARATOR_ENDPOINT=
SV_OCR_PROVIDER=off
SV_OCR_ENDPOINT=
```

实际 VLM 继续复用已有 `SV_VLM_ENDPOINT`、`SV_VLM_MODEL` 等配置。算法实现、模型、预处理及配置版本一并留痕；切换模型／规则使旧结果失效，不能只按图片哈希复用旧判定。新增照片只处理新增部分；修改现场说明后复用照片重判。

第一轮一个算法请求在运行，其余排队；CPU OCR 与 VLM 是否能并行，实测负载后决定。共享 GPU 时统一控制调度，不让两套模型各自抢满资源。超时／取消要覆盖实际推理进程；迟到结果按照片版本、哈希、标准版本、说明版本和尝试 ID 拒绝写回。

调试入口后续增加原图、定位图、裁片、OCR 原文／分数、VLM 输入输出，以及排队、解码／EXIF、检测、裁剪、OCR、VLM 和端到端耗时。当前调试主要覆盖 VLM，这些额外可视化仍需实现，不承诺已有。

## 7. 第一轮交付与验收

**算法同事提供：**可独立运行的代码与环境说明；几组输入输出；完整元件裁片与坐标映射；失败样例；模型版本及资源／耗时实测。两项能力可分别交付，不必同时准备完。

**本系统负责：**资产与身份转换、合同校验、编排／配置、队列与取消、当前 VLM 和正品分析兼容、结果落库／审计、预览／报告及回退。MES 和账号不由算法同事维护。

先过确定性检查，再进入真实模型与现场样片：

| 层级 | 需要证明什么 |
| --- | --- |
| L1 合同 | 零元件、重复 ID、遗漏、过期响应、矩阵不可逆／越界、错误哈希、实际资产不匹配会被拒绝 |
| L2 图像 | EXIF、多角度、长引脚、紧邻／重叠、边缘元件；裁片含完整元件，文字和位置能映射回原图 |
| L3 读文 | 1／2／3／4／6 件、弱光／反光／一般清晰度、长型号、前导零、S/5/O/0；保留错误证据，不借正品纠错 |
| L4 业务 | 新增只处理新增、替换不重复计件、说明变化重判、框选范围、人工改判留痕、失败不部分完成、回退只生成一套计件结果 |
| L5 对照 | 相同样本比较整图 VLM、分割＋VLM、分割＋OCR＋VLM；同时记录冷启动、热请求、排队与端到端耗时 |

建议起步整理 30～50 张有人工真值的照片，覆盖上述条件；这是发现问题用的小规模试验，不是正式上线准确率证明。训练／调参照片与验收照片分开，同一张照片拼接出的多个副本不能充当独立样本。

结果至少汇总：真实元件召回和误检、截断／漏件、整行逐字正确率、**不合格被误判合格**、误报、无法判定、耗时分布和峰值内存／显存。先明确哪些错误会影响业务，再商定阈值；不只比较“能否读出字”或平均耗时。CPU 内存、显存没有读数时明确写未测，不把模型文件大小当成运行占用。

## 8. 明天沟通时先确认这几件事

1. 定位是检测框、旋转框还是掩膜？能否返回完整元件和准确反向映射？是否已测长引脚、多件紧邻和非绿色背景？
2. OCR 是只识别已裁好的文字，还是也能检测文字位置？支持哪些字符／符号及方向？分数是什么含义？
3. 在 Windows／公司目标设备上怎么运行，是否必须 GPU？冷启动、单图热耗时、峰值资源分别多少？
4. 模块还是 HTTP 服务更方便？能否常驻、取消、超时返回，能否独立升级及回退？
5. 双方拿同一批哪些真实照片和人工真值联调？哪些异常只记录、哪些回退 VLM？

建议第一个里程碑只定为：**一张真实单件图，能够看见原图、定位、完整裁片、OCR 原文和现有 VLM 比对结果，任何一步失败能定位原因并回退。**跑通后再增加多件、批量和性能优化。
