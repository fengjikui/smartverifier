## 输入主要是图像展开部分

本次通过已加载模型的`count_tokens`对完整4件文字提示词（含C02／C03／C04／C06列表）分词，结果为**403 tokens**。未做生成推理。

- SDK返回`promptTokensCount=421`，不能把这当成包含完整视觉展开的总量。
- 引擎对应图像展开后的输入总量为约1803 tokens；相对纯文字多出的约1400主要包含视觉输入及聊天模板标记。不是严格拆分后的逐图token统计，也不是耗时百分比。
- 6件请求的展开后合计约2383 tokens；原数据只有SDK的431，进一步说明SDK这个字段没有反映完整视觉展开长度。
- 4件的两张PNG（正品＋白板）合计1,578,256字节，基础提示词1596字节；传输体积亦明显由图片构成。PNG字节、视觉token、模型计算量是不同指标，不可等同比较。

因此，本组输入长度和传输体积均主要在图像侧。视觉编码还存在额外计算，不能只靠上述token数推算精确的视觉耗时占比。

## 更好的服务器与vLLM缓存

[vLLM的APC说明](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)指出前缀缓存复用相同前缀的KV状态，主要减少prefill，不会直接加快逐token解码。[多模态缓存说明](https://docs.vllm.ai/en/latest/features/multimodal_inputs/#cached-inputs)还介绍了按图片内容哈希／稳定ID复用媒体处理；它与KV前缀缓存不是完全相同的缓存层。

后续服务器验证应分别测：

1. 同样输入首次／重复输入，记录缓存命中量、首token与解码速度。
2. 相同规则＋正品图，换新样品图，测实际可复用部分。
3. 改变标准、现场说明或元件编号之后的命中率与正确性。
4. 不同并发下的排队、单次延迟和总吞吐，避免只用低并发重复图的最好值。

更强GPU可能改善视觉处理和解码速度，但在设备未定前不预测具体倍数。缓存不会免除新照片的视觉处理或每件结果JSON的生成。

输入编排候选：固定通用规则 → 固定物料标准与正品图 → 现场说明、动态编号及新样品图。当前提示词把动态编号放在图片之前，可能较早截断可共享前缀。vLLM的[前缀缓存设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)把父块哈希与多模态内容计入匹配，必须核对模型实际渲染后的token顺序；这里只提出优化候选，尚未修改工作台或验证新编排。图片缓存也不能因“物料相同”就复用不同照片。

## Schema确实作为参数传入

当前链路：调试页选`JSON Schema` → `DebugRuns`生成`responseSchema` → Python工作器 → `LmStudioTransport.complete(..., response_format=schema)` → SDK `respond_stream(..., response_format=schema)`。

这是实际的生成约束参数，不是仅把Schema展示在网页上。提示词里的结构示例仍保留，是为了保持与提示词版实验一致；两者可以同时存在。日常检验主流程仍用提示词JSON＋后置校验，只有调试选项显式传生成Schema。

vLLM的OpenAI兼容Chat接口也支持独立参数，示意如下（`schema`应由服务端定义，不来自任意用户输入）：

```python
response_format = {
    "type": "json_schema",
    "json_schema": {"name": "inspection_result", "schema": schema},
}
```

`json_object`要求JSON形式，`json_schema`用于约束给定结构。亦可按版本使用`structured_outputs`参数；不复用已弃用的旧`guided_json`写法。参考[vLLM结构化输出文档](https://docs.vllm.ai/en/latest/features/structured_outputs/)。

结构Schema和业务提示有不同作用：可以省去提示词里重复粘贴的长格式模板，但仍要说明各字段含义、比较标准、允许差异、看不清时的处理。是否删掉结构示例应单独做准确性对照。Schema通过仍不保证读字正确、规则冲突完整或判断正确，后置校验继续保留。
